## 1. 🔍 事前コード分析・設計・リファクタリング分析

### 現状と再発メカニズムの分析

| # | 症状 | 根本原因 | 影響度 |
|---|------|---------|--------|
| ① | プリセットタスクが定期的に初期サンプル6個（子ども・家事・宅急便・電話・バグ・片付け）に巻き戻る | クラウド同期（`pullDataFromCloud()`）において、タスクやハビットにあるようなスマートマージ処理が存在せず、`state.taskPresets = cloudData.taskPresets;` と**無条件で配列ごと全上書き**していた。クラウド（GAS）側には以前保存された「初期サンプル6個」が残存していたため、15秒サイレントハートビート・タブ復帰・フォーカス・起動時の同期のたびにクラウドから古い6件が逆流し、ローカルを破壊していた。 | 致命的（データ巻き戻し・再発バグ） |
| ② | スマホ版（`mobile.js`）から同期が走るとクラウドのプリセットデータが消滅・空化する | `mobile.js` の `pushToCloud()` が送信するペイロードに `taskPresets`、`goals`、`manifesto` が含まれておらず、GAS側のプロパティストアが丸ごと置換されていたため、スマホ利用後にクラウドデータが初期化される時限爆弾となっていた。 | 高（複数端末運用崩壊リスク） |
| ③ | ローカルストレージ（`localStorage`）にサンプル6個が入ると手動復元しない限り戻らない | `loadTaskPresets()` は `localStorage` にデータがあればそのまま返し、実用プリセット（家事リセット、GS休憩、買い物、シャワー/風呂、ポスト確認など全11選）が欠落していても自動補正・マイグレーションするロジックが存在しなかった。 | 中〜高（復旧の手動依存） |

### 設計方針・リファクタリング戦略

1. **プリセット専用スマートディープマージエンジンの新設 (`mergeTaskPresetsDeep`)**:
   - `localPresets`、`cloudPresets`、`DEFAULT_TASK_PRESETS`（全11選）をIDおよびタイトル基準でスマート統合。
   - クラウド側から古いサンプル6個が届いても、ローカルの実用プリセット5選やユーザーが独自に作成したカスタムプリセットを絶対に消去せず最優先保護。
   - 複数端末でそれぞれ追加されたプリセットも欠落なく双方向合流（最大20スロットまで安全収容）。
2. **起動時・復元時自動マイグレーション (`loadTaskPresets`)**:
   - アプリ起動時やリロード時に、`localStorage` の内容を `mergeTaskPresetsDeep` で自動自己修復。
   - ユーザーが手動で「実用プリセット復元」ボタンを押す必要を完全にゼロ化。
3. **クラウド（GAS）マスター自動プッシュバック＆データ浄化**:
   - `pullDataFromCloud()` でクラウド側のプリセット件数がローカルより少ない（古い6件等）ことを検知した場合、マージ後の完全な11選＋カスタムプリセットを自動でクラウドへ即時プッシュバック（500msディレイ）し、クラウド側のマスターデータを最新化・恒久浄化。
4. **スマホ版（`mobile.js`）およびGAS同期スクリプト（`gas_sync_script.js`）の欠落防御**:
   - `mobile.js` の `STORAGE_KEYS` と同期ペイロードに `PRESETS`, `GOALS`, `MANIFESTO` を正式統合。スマホからのプッシュでクラウドデータが消滅する事故を100%遮断。
   - `gas_sync_script.js` にて、受信ペイロードにプリセット等が含まれない場合でも既存のプロパティストアを保護する二重防壁を配備。

## 2. 💡 「知ると面白い、今回の技術の仕組み」解説（エンジニア視点・ユーザー視点）

### ユーザー視点：「ボタンを押さなくても、クラウドと何度同期しても、絶対に愛用プリセットが消えなくなった」体験

「直したはずなのに、しばらく使っているとまた初期のサンプル6個に戻ってしまう…」
この現象は、**PCとクラウド（Google Drive）の間でデータの綱引きが起きていたこと**が原因でした。

PC側で「実用プリセット復元」を押してせっかく綺麗な11個（家事リセットやGS休憩など）に整えても、クラウド側には昔の「初期サンプル6個」が保存されたままでした。
Gendriveは非常に賢く、15秒ごとやブラウザのタブを切り替えた瞬間に「クラウドに新しい変更はないかな？」と自動チェック（サイレント同期）を行っています。このとき、クラウドから古い6個が届くと、**「クラウドのほうが正しい」と勘違いしてPC側の11個を6個に上書きしてしまっていた**のです。

今回の v1.9.7 では：
1. **「古いデータが届いても、消させない防壁」**: クラウドから古い6個が来ても、PC側の実用プリセット（全11選）やご自身で追加したプリセットを自動で守り抜くスマート合流エンジンを搭載しました。
2. **「クラウド側を逆に最新化して黙らせる」**: クラウド側が古い6個だと気付いた瞬間、PC側から「こっちが最新の11個だよ！」とクラウドへ自動で上書き送信し、クラウドの元データそのものを綺麗に掃除します。
3. **「手動ボタンの押下すら不要」**: アプリを開いたその瞬間に、裏側で自動マイグレーションが走り、常に完全なプリセット一覧が自動表示されます。

### エンジニア視点：無条件全上書きから「ID/タイトル二重結合スマートディープマージ」への昇華

#### 1. タスク・ハビットとのアーキテクチャ統一
Gendriveの同期エンジンにおいて、タスク（`mergeTasksDeep`）やハビット（`mergeHabitsDeep`）には高度な競合解決ロジックが組み込まれていましたが、プリセットタスク（`taskPresets`）だけが配列直代入（`state.taskPresets = cloudData.taskPresets`）という初歩的な脆弱性を抱えていました。

本改修では、プリセット専用の `mergeTaskPresetsDeep(local, cloud)` を配備：
```
[旧仕様: 破壊的全上書き]
cloudData.taskPresets (古い6件) ──> state.taskPresets = cloudData.taskPresets (ローカル消失！)

[v1.9.7: 三層ディープマージ防衛]
ローカル既存プリセット (最優先保護)
      +
クラウド側新規プリセット (他端末作成分合流)
      +
DEFAULT_TASK_PRESETS (実用11選の欠落自動補完)
      │
      ▼
mergeTaskPresetsDeep() ──> 最大20スロット内で完全合流・即時永続化！
      │
      └──> cloudPresets.length < merged.length を検知した場合、クラウドへ自動プッシュバック
```

#### 2. IDとタイトルの二重インデックス（Dual-Key Deduplication）
プリセットはユーザーによってIDが自動採番される場合（`T_...`）と固定ID（`preset_house_reset`）が混在します。
`seenIds`（ID集合）と `seenTitles`（タイトルトリム集合）の二重防壁で突合することにより、同一タイトルの重複増殖を100%防止しながら、未知のカスタムプリセットのみを安全に保持・合流させる堅牢なアルゴリズムを確立しました。
