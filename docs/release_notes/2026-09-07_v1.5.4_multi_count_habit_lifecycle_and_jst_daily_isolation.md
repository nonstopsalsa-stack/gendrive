## 1. 🔍 事前コード分析・設計・リファクタリング分析

### 課題の根本原因分析
「1日3回 水を飲む」「1日2回 コーヒーを飲む」などのハビットが、1回開始→完了にしただけで目標達成扱いになり画面から消えてしまう現象について、PC・スマホの全コードベースおよび実ストレージデータを徹底解析した結果、以下の4つの複合的構造障害を特定・解明した。

1. **スマホ版における多重回数解決ロジックの欠落（Mobile Truncation）**:
   - `mobile.js` の `getItemTargetTimes(item)` において、PC版の基幹である `item.recurrence.type === 'daily_times'`（`timesPerDay`）を評価するロジックが脱落していた。
   - `targetTimes` や `frequency` のみがフォールバック参照され、未設定時は一律 `1` が返される構造的縮退が生じていた。

2. **破壊的マイグレーションとクラウド同期を介した逆汚染（Cloud Propagation）**:
   - `mobile.js` の起動時マイグレーション `migrateMobileHabit` が、`targetTimes` が未定義のハビットに対し `migrated.targetTimes = 1` を強制代入して保存していた。
   - このスマホ版のローカルデータが GAS（Google Apps Script）クラウド同期を介して同期され、PC版のハビットオブジェクトにも `targetTimes: 1` が混入・逆汚染された。

3. **PC版判定エンジンの優先順位欠陥（Priority Inversion）**:
   - PC版 `js/engine/recurrenceEngine.js` の `getHabitTargetTimes(habit)` において、`recurrence.timesPerDay` よりも `habit.targetTimes` を先に評価していた。
   - このため、クラウド同期で混入した `targetTimes: 1` が本来の `recurrence.timesPerDay: 3` を乗っ取り、PC版でも目標回数が `1` と判定されて1回目の実行で即座に完了となっていた。

4. **UTC日付判定による早朝時間帯の日次リセット不発（Timezone Boundary Bug）**:
   - `app.js` の起動時サニタイザー `sanitizeDailyState` が `new Date().toISOString().slice(0, 10)`（UTC日付）で前日判定を行っていた。
   - 日本時間（JST）早朝0時〜9時前の起動時、UTCでは「前日（例: 9/6）」と判定されるため、日付境界のクリーンアップやリセットが正しく発火しない潜在的脆弱性となっていた。

### 設計・リファクタリング方針
- **Recurrence-First（再帰設定最優先）原則の確立**:
  - ハビットの目標回数を求める際、汚染の可能性がある外付けプロパティ `habit.targetTimes` より、マスター設定である `habit.recurrence.type === 'daily_times'`（`timesPerDay`）を最優先で参照。
- **自己修復エンジン（Self-Healing Migration）の組み込み**:
  - PC版（`storageService.js` / `migrateHabit`）およびスマホ版（`mobile.js` / `migrateMobileHabit`）の双方で、汚染された `targetTimes: 1` を自動検出し、本来の `timesPerDay` で上書き修復。
  - さらに、今朝1回の実行で誤って `done: true` / `status: 'completed'` になってしまった目標未達ハビット（`count < targetTimes`）を起動時に検出し、実績カウント（例: 1/3）を維持したまま未完了（`uncompleted`）へ自動救済。
- **多重防壁（Defense in Depth）による早期完了の絶対阻止**:
  - `app.js` の `getHabitStatusForSelectedDate` において、`targetTimes > 1` の場合は `curCount >= targetTimes` に達するまで絶対に `completed` にならないガードブロックを設置。
- **タイムゾーン境界の完全防御（JST Local Date Isolation）**:
  - `sanitizeDailyState` を `getTodayKey()`（ローカル日本時間 YYYY-MM-DD）に統一し、早朝起動時の日付跨ぎリセットを保証。

## 2. 💡 「知ると面白い、今回の技術の仕組み」解説（エンジニア視点・ユーザー視点）

### 🛠️ エンジニア視点：なぜクラウド同期が「バグの運び屋」になったのか？
```
【スマホ版起動】
  migrateMobileHabit() が未定義 targetTimes を一律 1 に強制上書き
       │
       ▼
【GAS クラウド同期】
  スマホ版のローカルデータ（targetTimes: 1）が Google Drive にアップロード
       │
       ▼
【PC版起動 & クラウド同期】
  クラウドからハビットデータを受信 ➔ PC版のハビットにも targetTimes: 1 が混入
       │
       ▼
【PC版 recurrenceEngine.js】
  getHabitTargetTimes(habit) が汚染された targetTimes: 1 を最優先で採用！
  （recurrence.timesPerDay: 3 が無視され、1回で完了判定へ）
```
今回の障害は、**「スマホ側の単なるデフォルト補完（フォールバック）が、クラウド同期によってPC版のコアエンジンを逆汚染し、PC側の評価優先順位のバグと共鳴して顕在化した」**という分散システム特有のエッジケースである。
これを根絶するため、本改修では「優先順位の是正」と同時に「受信時に自動で自己治癒（Self-Healing）するマイグレーションフィルター」をPC・スマホの両端に二重展開した。

### 👤 ユーザー視点：今朝の「1回やった分」はどうなる？
- 「1回やったのに消えてしまった今朝の履歴はどうなるのか？」という不安に対し、Gendrive は**実績カウントを破棄せず、誤って立った完了フラグだけを自動で解除する救済機能**を実装した。
- ページを開いた瞬間に自己修復エンジンが走り、今朝の「1回目」の記録を保持したまま、バナーの表示が「1/3」の未完了状態へと自然に戻る。
