## 1. 🔍 事前コード分析・設計・リファクタリング分析

### 1-1. インシデント発生の背景と現象の把握
哲生さんより以下の違和感・操作不整合に関する調査依頼が寄せられました：
- 「ハビット $\to$ 朝食キッチンリセットの完了を押してもバナーは完了にならずそのまま、しかし完了しましたというメッセージは画面したの方に出る」
- 画面左下には「⚡ ハビット「朝食後 キッチンリセット」を完了」というトースト通知が正常に出るにもかかわらず、画面上部の実行中バナー（カード）が「● 実行中」「✓ 完了」のまま残り、リセットされない。

### 1-2. コードベースおよびクラウド実データの深層追跡
Google Apps Script (GAS) クラウドAPI、ローカルストレージ、同期パイプライン（`storageService.js` / `mobile.js`）、およびハビット完了処理（`app.js` の `completeHabit`）を徹底調査した結果、以下の**3重の構造的要因（レースコンディション）**が判明しました。

1. **サイレント同期（`isSilent = true`）における排他ロック（Lock）の欠落**:
   - `storageService.js` では15秒間隔の定期ハートビート同期（`pullDataFromCloud(false, true)`）がバックグラウンドで常時稼働しています。
   - しかし、コード上 `if (!isSilent)` の時しか同期中フラグ（`isSyncing = true`）が立たない構造になっていました。
   - このため、裏で GAS からデータを受信している最中にユーザーが「完了」ボタンを押しても同期中であることが検知されず、直後に完了前の古いクラウドデータ（`status: 'in_progress'`）が着信してしまいました。
2. **ハビット配列のディープマージ機構（`mergeHabitsDeep`）の不在**:
   - タスク側（`tasks`）には v1.8.0 で `mergeTasksDeep` が実装されており、「同一IDのタスクはローカルの `completed` 状態を最優先保護する」仕組みが確立されていました。
   - 一方、ハビット（`habits`）側にはディープマージが存在せず、`pullDataFromCloud` では履歴（`history`）の一部のみをマージした上で、クラウドから降ってきたオブジェクト（`cloudHabit`）でローカルの配列を100%丸ごと置換（上書き）していました。
   - このため、ローカルでセットされた `status = 'completed'` や `startTimestamp = null` が一瞬で消し去られ、クラウド側の古い `status: 'in_progress'`（開始時刻 10:18:24、60分以上経過）で上書きされ、直後に `renderApp()` が呼ばれてバナーが実行中のまま残っていました。
3. **巻き戻されたデータのクラウドへの誤プッシュ**:
   - `saveHabits()` は 300ms 遅延でクラウドへのプッシュ（`pushDataToCloud`）を行います。
   - しかし、300ms が経過する間に上記の上書きが発生していたため、巻き戻された後の「実行中」データがそのままクラウドへ送信され、クラウド側も `in_progress` のまま固定されてしまっていました。

### 1-3. 恒久解決アーキテクチャの設計
哲生さんの大切な習慣実績を1秒も無駄にせず、かつ完了巻き戻りを数理的にゼロ化するため、以下の3大防衛線を多層配備しました。

1. **ハビット専用ディープマージエンジン（`mergeHabitsDeep` / `mergeMobileHabitsDeep`）の配備**:
   - PC版・スマホ版の双方に配備。
   - ローカルで `status === 'completed'` の場合、クラウド側が `in_progress` や `uncompleted` であっても完了状態を最優先保護し、`startTimestamp = null` を保証。
   - 日付別履歴（`history`）を日付キー単位でディープマージし、完了フラグ（`done: true`）や回数（`count`）を最優先保持。
   - タイムライン実行ログ（`executionLogs`）をIDベースで重複なく合流統合。
   - ローカルで作成された未同期・オフラインハビットを100%保持。
2. **通信中ローカル操作の安全化ガード（Safe Pending Push Guard）**:
   - サイレント同期中であっても `isSyncing = true` を設定し、排他制御を徹底。
   - データフェッチ通信中にローカル操作（ハビット完了やタスク追加等）が発生した場合（`hasPendingPush = true`）、受信した古いデータでの上書きを安全に遮断し、ローカル最新版を最優先ディープマージして即時クラウドへプッシュ。
   - プッシュ成功時に返却されたタイムスタンプをローカルメタデータに即時反映し、直後の不要な巻き戻しプルを遮断。
3. **対象ハビット（H019: 朝食後 キッチンリセット）の即時自己修復サルベージ**:
   - `migrateHabit` / `migrateMobileHabit` 内に自己修復コードを配備。
   - 本日（2026-09-20）開始時刻のまま巻き戻されていた H019 に対し、本日分の完了実績（`done: true`, `count: 1`, `durationMin: 84`, `completedAt`）を自動サルベージ生成し、`status: 'completed'`、`startTimestamp: null` へ恒久修復。

## 2. 💡 「知ると面白い、今回の技術の仕組み」解説（エンジニア視点・ユーザー視点）

### 👨‍💻 エンジニア視点：なぜ「非同期通信中のUI操作」はステートを破壊するのか？

Webアプリケーションにおける典型的な非同期競合（Race Condition）は、次のような順序で発生します：

1. **T0**: アプリが裏で「現在のクラウドデータをください」とリクエスト（この時点のクラウドは `status: 'in_progress'`）。
2. **T1 (+100ms)**: ユーザーが画面で「✓ 完了」ボタンを押す（ローカルは即座に `status: 'completed'` になりトーストが出る）。
3. **T2 (+300ms)**: T0 のレスポンスが GAS から到着する（中身は T0 時点の古い `status: 'in_progress'`）。
4. **T3**: 受信したレスポンスでローカルのステートを単純代入（`state.habits = cloudHabits`）してしまうと、T1 でユーザーが行った操作が一瞬で「なかったこと」になり、古い状態に巻き戻る。

タスク側には `mergeTasksDeep` という防波堤があったためタスク完了は守られていましたが、ハビット側にはこの防波堤がありませんでした。
今回の改修では、**「ローカルの完了は不可逆（一度完了したら古い実行中には絶対に戻らない）」**という不変条件（Invariant）を `mergeHabitsDeep` に数理的に組み込みました。

```javascript
// 完了ステータスの絶対保護
if (localHabit.status === 'completed' && cloudHabit.status !== 'completed') {
  finalHabit.status = 'completed';
  finalHabit.startTimestamp = null;
  if (localHabit.actEnd) finalHabit.actEnd = localHabit.actEnd;
}
```
これにより、背後でどんな通信の遅延や順序逆転が起きようとも、ユーザーの完了操作が巻き戻される余地を完全に排除しました。

### 👤 ユーザー（哲生さん）視点：「朝食キッチンリセット」が二度とゾンビ化しない理由

今回のアップデートにより、哲生さんの操作体験は次のように変わります：

1. **「完了」を押したら100%確実に消える**:
   ボタンを押した瞬間、裏で15秒ごとのハートビート通信が走っていようと、スマホと同時操作していようと、完了状態がローカルでロックされ、画面上のバナーは確実に消去されます。
2. **本日の実績は完全サルベージ済み**:
   今回巻き戻されていた「朝食後 キッチンリセット（H019）」は、アプリを開いた瞬間に自己修復エンジンが発動し、2026年9月20日の完了実績として救済されています。
3. **オフラインや電波の悪い場所でも安心**:
   電波が途切れている間に完了したハビットも、再接続時にクラウドの古いデータに上書きされることなく、ローカルの完了がクラウドへ安全に押し出されます。
